# 代码审查流程

对一份 diff 或一个模块做 review 时:

1. **先看意图**:读 commit message / issue,明确这次改动想解决什么
2. **正确性优先**:边界条件(空输入/负数/None)、错误处理、资源释放
3. **对照测试**:改动是否有测试覆盖?现有测试是否会被破坏?
4. **再看风格**:命名、重复代码、超长函数——只在正确性无虞后提
5. **输出格式**:按严重程度分级(blocker / suggestion / nit),每条给出文件:行号与修改建议

原则:
- 指出问题时必须能说明"什么输入会触发什么错误行为"
- 不确定的问题标注为 question 而不是断言
